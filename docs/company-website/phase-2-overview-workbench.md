# Phase 2：业务总览与工作台

## 1. 阶段定位

Phase 1 已建立客户、项目、任务、跟进及跨模块关联管理能力。Phase 2 在既有业务记录基础上，提升日常业务判断、执行与复盘效率，不另建独立系统。

目标：从分散的业务记录管理，逐步升级为统一的日常业务决策与执行工作台。

## 2. 子阶段路线

| 子阶段 | 目标 | 交付重点 |
|---|---|---|
| 2-A | 业务总览首页 | KPI、需要关注、近期业务、快捷导航 |
| 2-B | 待办事项中心 | 统一处理逾期任务、今日/未来任务和待跟进事项 |
| 2-C | 项目与客户业务概况 | 项目状态分布、项目进度、客户项目关联、近期活动 |
| 2-D | 业务趋势与周期复盘 | 周/月项目完成、任务处理、客户跟进趋势 |

实施顺序为 2-A → 2-B → 2-C → 2-D；每个子阶段独立开发、验证和验收。先解决日常操作，再逐步增加分析能力。

## 3. 共通技术原则

- 沿用 daily_weekly_planner 现有个人公司网站工作区、账号认证和三语能力。
- 继续使用 Supabase 项目 kopvznygsqsheibsjjvv、public.company_records 与生产 company-api v5。
- 业务统计优先从现有记录实时计算，不额外保存可重复计算的汇总数据。
- 分页数据必须读取完整结果集并核对接口 total；不得仅用第一页计算全量 KPI。
- 不擅自新增表/字段、修改 RLS、迁移或 Edge Function。若当前接口不能满足准确性或性能要求，先提出影响和方案。
- 统计失败与空数据必须区分；不完整读取不得显示为准确的 0。
- 保持客户、项目、任务、跟进 CRUD、项目自动进度联动、跨模块导航和任务截止日期筛选。
- 简体中文、English、日本語；兼容桌面与移动端。

## 4. 阶段验收原则

每个子阶段记录需求口径、数据来源、分页/错误处理、自动化验证、PR 与部署结果，并由用户在生产 Pages 真实浏览器验收。代码合并、Pages 部署和用户验收是三个独立状态。
