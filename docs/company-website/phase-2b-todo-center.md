# 阶段 2-B：待办事项中心

## 1. 目标

在现有个人公司网站工作区增加统一待办中心，将需要处理的任务和客户跟进集中呈现，减少在任务列表与业务跟进列表之间反复切换的成本。

## 2. 待办分组与口径

### 任务
- 逾期任务：due_date 早于浏览器本地今天，且 status 不为 completed。
- 今日任务：due_date 等于浏览器本地今天，且 status 不为 completed。
- 未来 7 天任务：从明天起连续 7 个日历日（明天至今天 + 7 天，含第 7 天），且 status 不为 completed；今天单独归入今日任务，避免重复。
- 未设置截止日期的任务：due_date 为空或不是有效 YYYY-MM-DD 日期，且 status 不为 completed。

### 客户跟进
- 待处理跟进：status=pending 的所有 follow_up 记录，不因 next_follow_up_date 是否为空而丢失。
- 按 next_follow_up_date 升序排列；无下次跟进日期的记录放在末尾。
- 每条跟进显示下次跟进日期状态：已逾期、今天、已安排、未设置下次跟进日期。
- 已完成跟进不进入待办中心。

## 3. 交互

- 在现有公司业务导航增加「待办中心」入口，与业务总览、客户、项目、任务、业务跟进并列。
- 分组标题显示该组记录数量；空组保留轻量空状态，全部分组均为空时显示统一空状态。
- 点击任务打开既有任务编辑窗口；点击跟进打开既有跟进编辑窗口。
- 继续使用原有记录 CRUD 和项目/客户关联，不新增第二份待办数据，不新增独立完成状态。
- 保存或删除记录后，如果用户仍在待办中心，刷新当前待办数据。
- 提供简体中文、English、日本語及桌面/移动端布局。

## 4. 数据读取与错误处理

- 使用 company-api v5 的分页 GET /records 接口读取 task、follow_up、project、customer。
- 每页 limit=100；按 total 连续读取并校验分页期间 total 一致、页面未提前结束、最终数量等于 total。
- 分页失败或接口报错时显示错误，不把失败显示为空待办。
- 读取完整项目和客户数据，以保证待办项的项目/客户上下文不局限于第一页。
- 当前实现不持久化待办快照，进入待办中心时读取最新业务记录。V10.58 起：进入时最多复用 15 秒内已完整读取的数据，点击「刷新」重新读取，任何新增/编辑/删除都会清空缓存（见 [V10.58](./v10-58-complete-reads.md)）。

## 5. 技术边界

- 沿用 public.company_records、现有认证和 company-api v5。
- 不修改数据库 schema、migration、RLS、Edge Function、认证或生产业务数据。
- 不改变现有任务/跟进状态定义、CRUD、项目进度自动联动、业务总览和关联导航。
- 不将任务完成按钮另做一套状态逻辑；通过既有编辑窗口更新状态。

## 6. 验收标准

1. 逾期、今日、未来 7 天和无截止日期任务分组准确，已完成任务不出现。
2. 未来 7 天与今日分组互斥；未来 7 天指明天至第 6 天。
3. 待处理跟进全部出现，按下次跟进日期排序，无日期项排在末尾；已完成跟进排除。
4. 任务和跟进均可直接打开原记录编辑窗口，所属项目/客户上下文正确。
5. API 失败或分页不完整时显示错误；真正无待办时显示空状态。
6. 保存/删除后重新进入或刷新待办中心，数据与业务列表保持一致。
7. 三语、响应式；业务总览、客户/项目/任务/跟进 CRUD、项目进度联动和跨模块导航不回归。
