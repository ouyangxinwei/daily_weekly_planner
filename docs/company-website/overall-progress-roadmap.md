## 4. Phase 2：业务总览与工作台

### 阶段目标
从“业务记录管理”升级为“日常业务决策与执行工作台”，把客户、项目、任务和跟进信息放在统一入口中，帮助快速判断当前业务状况和下一步行动。Phase 2 分阶段交付，不一次性堆叠所有分析能力。

| 子阶段 | 范围 | 优先级/状态 |
|---|---|---|
| 2-A | 业务总览首页：核心 KPI、需要关注、近期业务及快捷导航 | **第一优先级，开发中** |
| 2-B | 待办事项中心：统一处理逾期任务、今日任务、未来任务和待跟进事项 | 后续阶段 |
| 2-C | 项目与客户业务概况：项目状态分布、进度、客户项目关联及近期活动 | 后续阶段 |
| 2-D | 业务趋势与周期复盘：按周/月观察项目、任务和客户跟进趋势 | 后续阶段 |

### 2-A：业务总览首页（当前实施）
- 在现有个人公司网站工作区内增加“业务总览”入口，不建立独立系统；客户、项目、任务、业务跟进入口和 CRUD 流程保持不变。
- KPI：客户总数、进行中项目、未完成任务、待处理跟进。
- 需要关注：逾期任务、今日到期、未来 7 天到期、逾期待跟进。
- 近期业务：最近更新项目、最近创建/更新任务、最近客户跟进记录。
- 点击 KPI/关注项进入对应模块及筛选结果；近期记录可跳转至详情或编辑入口。
- 日期口径沿用 1-I-E：浏览器本地日期；逾期为早于今天且未完成；未来 7 天为今天至第 6 天（含今天）。逾期待跟进为下次跟进日期早于今天且状态为待跟进。
- 提供简体中文、英文、日文及桌面/移动端布局。

### 2-A 数据与实现边界
- 复用 company-api v5 的 /customers、/records 分页接口及 public.company_records 现有记录，不创建统计数据副本。
- 列表接口单页最大 100 条；总览必须根据接口 total 连续分页，不能把第一页当作全量。
- 现有 fetchAllRecords 默认有 10,000 条上限；2-A 必须避免在未提示的情况下将截断结果当成精确总数。接口 offset 上限为 1,000,000，达到边界或返回不完整时，应明确显示统计不可完整读取，而非显示为 0 或伪精确值。
- 客户总数统计所有客户记录，不因潜在/合作中/暂停合作状态排除；进行中项目按 status=active；未完成任务按状态非 completed；待处理跟进按 status=pending。
- 跟进字段沿用 data.customer_id、data.project_id、next_follow_up_date；项目、任务关系沿用 parent_record_id。
- 不新增数据库字段/表，不修改 migration、RLS、认证、company-api 或生产业务数据。若现有接口能力不足，先评估并说明，不擅自扩大范围。

### 2-A 验收标准
1. KPI 与现有完整列表数据一致，不能仅统计当前分页。
2. 关注项日期边界、状态排除与 1-I-E 口径一致。
3. 点击统计项进入正确模块和筛选结果。
4. 近期项目、任务、跟进排序稳定，点击后能打开相应记录。
5. 空数据显示 0；API 失败或分页不完整显示错误/不完整状态，不得伪装成 0。
6. 新增、编辑、删除记录后重新加载总览，统计与近期记录同步更新。
7. 三语、响应式布局；现有 CRUD、项目自动进度联动、跨模块导航和 1-I-E 日期筛选不回归。

### 后续子阶段
- 2-B 待办事项中心：统一任务和待跟进事项的处理入口，支持状态/日期分组与直接跳转。
- 2-C 项目与客户业务概况：呈现项目状态分布、进度、客户关联及近期活动。
- 2-D 业务趋势与周期复盘：提供周/月维度的项目完成、任务处理、客户跟进趋势。

时间估算（规划参考）：2-A 约 1–2 天；2-B 约 1–2 天；2-C 约 1–2 天；2-D 约 2–3 天，均不含部署等待与真实浏览器验收。

## 5. 每次重新开始时的接续规则

重新打开项目时，先读本文，再读对应阶段文档。按以下顺序继续：

1. 确认 GitHub 仓库 `ouyangxinwei/daily_weekly_planner` 的 `main` 最新提交和当前 Actions 状态。
2. 查看本文的“当前完成位置”和“下一步”。
3. 当前 Phase 2 从 2-A 业务总览首页开始；先完成数据口径和分页完整性核对，再实施功能。
4. 功能开发从最新 `main` 创建独立分支；不直接在 `main` 开发。
5. 沿用现有数据库和生产 `company-api` v5，除非用户明确批准架构变更。
6. 按必要范围做静态检查和针对性验证；不把 Playwright 浏览器安装或完整 E2E 作为默认合并前提。
7. PR squash merge 后检查 GitHub Actions 的 build 和 deploy。只有两者成功，才能报告 Pages 已部署。
8. 部署后由用户进行真实浏览器验收；收到“验收 OK”后更新阶段文档和本文状态。
9. 不把“代码已合并”“Pages 已部署”“用户已验收”混为同一个状态。
