# Phase 3-C-A：统一经营决策台（V10.63.0）

## 1. 目标

把已有客户、项目、任务、业务跟进、交易收支与活动历史整合到一个经营决策入口。重点不是重复展示已有图表，而是回答：

- 目前业务规模和执行状态如何？
- 哪些事项最需要优先处理？
- 最近 12 个月各币种实际收支和预计收支如何？
- 最近哪些业务记录发生了变化，应该继续查看什么？

本阶段在现有个人公司网站内新增入口，不建立独立系统，不改变现有 CRUD 流程。

## 2. 交付范围

### 经营 KPI
- 客户总数、进行中项目、未完成任务、待处理跟进、交易记录数。
- KPI 只反映现有记录状态，不推断合同金额、客户价值或利润。

### 优先行动建议
按紧急程度归类并支持跳转：
- 紧急：逾期任务、逾期项目、逾期待跟进。
- 高优先级：受阻任务、今日到期任务。
- 建议关注：未来 7 天到期任务/项目、没有安排下次日期的待跟进、未关联项目的未完成任务。

### 财务概况
- 按 JPY / CNY / USD 独立统计最近 12 个自然月。
- 分开展示已完成收入、已完成支出、净现金流、预计收入和预计支出。
- 不做汇率换算，不跨币种合计。
- 净现金流仅为已录入交易的收入减支出，不等同于会计利润、毛利或可用现金余额。

### 活动与记录
- 汇总最近更新的客户、项目、任务和跟进记录。
- 活动历史复用 V10.62 GET /activity-history，读取最近更新的 6 条当前记录各自的最新活动，再合并排序。
- 这是受现有按 record_id 查询 API 约束的近期活动视图，不宣称是完整全局审计流；已删除记录不会作为候选记录出现。
- 历史为空时按真实空状态显示，不推断此前没有活动。

## 3. 技术实现

- 新增纯规则模块：company-decision-center.js。
- 前端入口与渲染：company-business.js。
- 样式：company-business.css，支持窄屏布局。
- 业务数据经 company-record-loader.js 严格分页读取，复用短时缓存。
- 收支计算复用 getMonthlyCashflow 与 BigInt 微单位金额格式化。
- 活动历史使用现有 company-api Basic 认证与 owner 隔离。
- 不新增数据库表、字段、RPC、RLS policy 或 Supabase migration；不修改生产业务数据。

## 4. 明确不做

- 不将不同币种换算后相加。
- 不将净现金流称为利润。
- 当前没有可靠成本/工时数据，不计算项目利润率、客户终身价值或投资回报。
- 不对客户或项目做 AI 自动评分，不生成未经数据支持的预测。
- 不运行 Nightly Playwright；真实浏览器验收由用户方便时进行，不阻断后续独立开发。
