# Phase 3-D：项目交付与资源规划

## 目标
在现有客户、项目、任务、进度和活动历史基础上，逐步增加透明、可解释的项目交付与资源分析。各子阶段独立交付，优先复用现有数据，不提前扩大数据库/API 范围。

## 子阶段

### Phase 3-D-A：项目计划进度与实际进度偏差分析
- 状态：V10.66.0 功能已在 `feat/phase-3d-a` 实现，等待 PR 验证与合并。
- 复用项目 `start_date`、`due_date`、`data.progress_percent` 和 `status`。
- 根据项目起止日期线性估算日历计划进度，与当前实际进度比较。
- 明确区分进度偏差、已超期、日期缺失和日期配置错误。
- 不新增 DB/API，不修改生产业务数据。
- 具体规则见 [Phase 3-D-A 实施记录](./phase-3d-a-project-delivery-analysis.md)。

### Phase 3-D-B：任务依赖和延期风险（后续）
- 在现有任务状态、截止日期和所属项目基础上，先梳理可用风险证据。
- 若引入依赖关系，必须提供明确可维护的数据结构，并检测无效依赖和循环。
- 不把任务列表顺序推断成依赖关系，不做黑箱预测。

### Phase 3-D-C：交付日期与客户承诺日期（后续）
- 项目内部预计完成日期与对客户承诺的交付日期必须分开。
- 不得把现有 `due_date` 自动解释为客户承诺日期。
- 优先评估 JSONB 可选字段和兼容策略，确定后再增加编辑界面。

### Phase 3-D-D：工作量和人员资源分配（后续）
- 现有任务没有稳定的负责人、估算工时和实际工时字段。
- 未来可评估可选的负责人、估算工时和实际工时字段；空值代表未知，不代表零。
- 初期只做工作量分布与资源可见性，不做人事绩效评价。

## 实施原则
1. 复用 company_records 和现有完整分页读取缓存。
2. 除非子阶段明确批准，不改变数据库、RLS、Edge Function、company-api、认证或生产数据。
3. 纯分析规则模块化、独立测试，输入现有记录并输出可解释结果。
4. 对缺失/错误数据明确提示，不伪造精度，不把未知当作 0。
5. 支持简体中文、英文、日文和响应式布局。
6. 每个子阶段独立版本、文档、专项验证和 PR；合并前确认范围与关键测试。
