# V10.58：公司业务记录完整读取与限流保护（修复）

> 修复，不是新阶段。不修改 Supabase 表结构、迁移、RLS、company-api 或业务数据格式。

## 1. 问题

对 `886ad81` 的核查发现，Phase 1 的部分列表读取不能保证数据完整：

| # | 问题 | 影响 |
|---|---|---|
| 1 | `getRelationshipRecords()` 用 `['project','task','follow_up'].map(fetchAllRecords)` 读取关联记录。`Array.map` 会把数组下标（0、1、2）作为第二个参数 `maxRecords` 传入，结果每种记录**只读第一页的 100 条** | 客户卡片上的关联数量和预览、项目详情里的关联任务和跟进可能不完整（1-I-B、1-I-D） |
| 2 | `fetchAllRecords()` 遇到空页就停止，不校验 `total` 是否一致和最终数量；默认上限 10,000 条。任务列表的截止日期筛选也用它读取 | 任务筛选和分页可能在用户不知情时基于不完整数据（与 1-I-E「对完整结果集计算并分页」不符） |
| 3 | 跟进和项目的关联筛选（按客户、按项目、逾期待跟进）使用同样不校验完整性的分页循环 | 同上 |
| 4 | `loadCustomers()` 只读取前 100 个客户和前 100 个项目 | 超过 100 个后，编辑器的客户/项目选项和项目筛选下拉不完整 |
| 5 | company-api 限制每个 IP 每 60 秒 30 次请求；任务页每次修改筛选条件或翻页都会重新全量读取 | 连续操作容易触发 429；429 也只显示为通用的「操作失败」 |

## 2. 修复

- 新增纯函数模块 `company-record-loader.js`：
  - `fetchCompleteList()`：每页 100 条连续读取，要求每页 `total` 一致；在达到 `total` 之前出现空页或短页、最终数量不等于 `total`、`offset` 超过 1,000,000 时，一律报错，不返回部分数据。
  - `createRecordCache()`：按请求路径缓存完整结果；相同的读取同时进行时共用一组请求；`maxAgeMs` 控制可以复用多久以前的结果；读取失败不缓存；`invalidate()` 清空全部缓存。
- `company-business.js`：
  - 项目、任务、跟进（以及工作台的客户）的完整读取统一使用 `loadRecords()`；编辑器和筛选用的客户列表沿用 `GET /customers`，同样逐页完整读取（`loadCustomerList()`）。两者都经过上述缓存；删除 `fetchAllRecords()`。
  - 2-A～2-D 工作台、任务截止日期筛选、跟进/项目关联筛选、关联信息、编辑器选项都使用完整数据。
  - 关联信息读取失败时，客户卡片显示「—」和「关联信息暂时无法读取」，不再显示为 0 条。
  - 429 显示「请求过于频繁，请等待约 1 分钟后再刷新」（中、英、日）。
- `company-records-workspace.js`（3-A）：客户和项目改为复用上述缓存；交易、文档、附件的读取增加短页和最终数量校验。

## 3. 数据新鲜度规则

| 操作 | 可复用多久以前读取的数据 |
|---|---|
| 进入工作台或列表标签 | 15 秒 |
| 同一页面内修改搜索、筛选或翻页；打开编辑器；关联预览；切换语言 | 60 秒 |
| 点击「刷新」 | 0（重新读取） |
| 新增、编辑、删除业务记录 | 清空缓存，下次读取一定是最新数据 |

说明：2-B 文档原写「进入待办中心时读取最新业务记录」，现改为「最多复用 15 秒内读取的数据；点击刷新会重新读取」。其他设备上的修改最多延迟 60 秒才会在筛选和翻页中出现，点击刷新可以立即看到。

请求次数（每种记录 ≤100 条时）：进入任务页 3 次（客户、项目、任务），之后修改筛选或翻页 0 次；以前进入任务页需要 3 次，之后每次修改还要再发 3 次。15 秒内在业务总览、待办中心、项目与客户概况之间切换，共用同一份数据。
