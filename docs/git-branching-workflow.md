# Git 分支与日常开发规则

> 本文是本仓库当前唯一权威的分支与日常开发约定。核心原则：**日常只使用 main，修改后优先在真实页面验证；测试按需进行；部署结果必须实际确认。**

## 1. 分支规则

| 分支 | 用途 | 状态与规则 |
|---|---|---|
| `main` | 唯一日常开发分支，也是 GitHub Pages 正式发布分支 | 日常功能、修复、文档和版本维护均直接在此进行 |
| `development` | 历史开发分支 | 暂停维护、暂时保留；不作为日常开发、测试、合并或同步前置条件 |

- 日常开发不要求创建功能分支。
- 日常开发不要求创建或合并 Pull Request（PR）。
- 不再要求 main 与 development 保持同步；development 暂停维护期间允许与 main 出现差异。
- 除非用户明确要求或存在特殊技术需要，不主动恢复 development 的维护。

## 2. 日常开发流程

1. 确认仓库和当前工作区，日常修改直接在最新的 `main` 上进行。
2. 先理解现有实现和影响范围，再做最小必要修改。
3. 完成修改后，优先通过真实页面验证用户关心的功能和交互。
4. 本地测试、自动化测试、构建和 GitHub Actions 均按变更风险与实际需要决定，不是每次开发的前置条件。
5. 如果没有执行某项测试，明确记录为「未执行」或「待验证」，不得描述为通过。
6. 对需要用户设备、真实账号或特定环境的行为，列明待用户确认的项目。
7. 按现有版本规范维护版本声明、三语 CHANGELOG、Release 和必要的 Service Worker 缓存版本；纯文档变更是否需要更新版本号，仍按既有规范判断。

## 3. 测试与页面验证

- **优先级：** 真实页面验证优先；其他测试根据实际风险选择。
- 不要求每次修改都运行完整测试套件、Playwright E2E 或 GitHub Actions。
- 低风险、局部或文档修改可采用代码审查和针对性页面检查。
- 涉及核心业务逻辑、数据迁移、权限、安全、云端写入或高影响操作时，应选择足以覆盖风险的验证方式。
- 不为追求绿色结果而删除有效断言、跳过失败测试或虚报通过。
- 本地页面或联调环境可能连接正式 Supabase；任何测试写操作前必须确认数据影响，避免污染真实数据。
- 页面测试未覆盖的浏览器、手机或账号行为应明确标注，不能声称已验证。

## 4. Actions 与 CI

- GitHub Actions 不作为每次开发的启动条件、提交条件或日常开发前置门槛。
- 当变更风险较高、需要构建/自动化验证、用户明确要求，或发布流程要求时，再运行适用的 Actions。
- Actions 未运行、运行中、失败或结果无法确认时，必须如实报告。
- Actions 通过只代表对应工作流检查通过，不自动证明真实页面行为或正式部署完成。

## 5. 部署与交付确认

1. GitHub Pages 的正式发布来源仍为 `main`。
2. 代码提交、推送或 Actions 启动都不等于部署成功。
3. 只有确认与目标 `main` 提交对应的 GitHub Pages 构建和部署实际成功，才能报告「已部署」。
4. 如果部署未运行、失败、仍在进行或无法对应到目标提交，分别报告「未部署」「部署失败」「部署中」或「状态待确认」。
5. 正式站地址：https://ouyangxinwei.github.io/daily_weekly_planner/

## 6. 版本管理

- 继续遵守仓库现有版本规范。
- 正式应用版本发布时，按要求同步根目录 `VERSION`、`package.json`、三语 CHANGELOG、Release 及相关缓存版本声明。
- 不因本规则调整而跳过版本号核对、Release 记录或部署确认。
- 纯文档维护按现有文档维护规则处理，不擅自制造应用版本发布。

## 7. 未完成事项记录

暂时无法解决的问题必须标记为「未完成」，并记录：
- **现象：** 当前发生了什么，如何复现。
- **原因：** 已确认原因；尚未确认时写「原因待查」。
- **影响：** 影响的功能、数据或用户流程。
- **下一步：** 后续检查或修复动作及必要依赖。
- **是否阻塞：** 若不影响其他独立工作，应继续推进并保留记录。

---

**简明规则：只在 main 日常开发 → 优先真实页面验证 → 测试和 Actions 按需 → 版本规范继续执行 → 实际确认部署结果。**
