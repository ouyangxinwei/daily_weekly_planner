# Git 分支与固定开发工作流

> 本文是本仓库唯一权威的分支与日常交付约定。业务变更固定流程为：**development 开发与风险审查 → 按需验证 → 经明确许可合并 main → GitHub Pages 正式部署**。纯架构/维护文档适用第 2 节的文档专用例外。本机无法运行测试时，不要求用户进行本地测试。

## 1. 长期保留的分支

| 分支 | 用途 | 生命周期 | 操作规则 |
|---|---|---|---|
| `main` | 稳定版本与 GitHub Pages 正式部署 | 永久 | 接收经明确许可的业务集成；允许按文档专用例外直接提交纯文档变更 |
| `development` | 所有日常功能、修复、文档和版本维护 | 永久 | 默认开发分支；直接在此分支持续完成开发和验证 |
| `feat/agent-plan-steps` | Agent 工作流实验及历史执行证据 | 特别保留 | 独立隔离，不参与日常开发和常规清理；删除必须先获得所有者明确许可 |

除上述三个分支外，默认不创建或长期保留其他分支。只有技术限制、外部协作或隔离验证确实需要时，才考虑短期分支。

## 2. 固定开发与交付流程

## 2.0 纯文档维护专用例外

以下规则适用于不改变业务逻辑、页面行为、数据库结构/数据、API 契约、权限、部署配置或应用运行资源的纯文档变更（例如架构说明、维护指南、审查报告和进度报告）：

1. 可直接在 `main` 创建/更新 Markdown 文档，不需要为此建立功能分支或等待业务 PR 合并许可。
2. 提交后将 `development` 快进同步到同一 `main` 提交，确保两个长期分支的文档版本一致。
3. 如果 `development` 有独立提交、存在分叉或快进失败，停止同步并先审查差异；禁止 force push、reset 或丢弃任一分支提交。
4. 纯文档变更不更新应用版本号、CHANGELOG 或 Service Worker cache name，也不触发 Pages 部署要求；若包含代码、配置、数据库或业务行为变化，则不适用本例外。
5. 夜间 Agent 运行完成后，只有在结果属于纯文档维护且没有未审查的业务变更时，才按本规则同步 `main` 与 `development`。Agent 不得借此修改规范正文、业务代码或自动合并业务 PR。



业务功能开发、缺陷修复和代码/配置变更遵循以下顺序。纯文档维护按下方「文档专用例外」执行，不要求创建功能分支或业务 PR。不得将本地测试作为用户必须完成的前置条件；按风险选择必要验证。

### 阶段 A：在 development 开发

1. 开始前检查工作区和远程分支状态，切换到最新的 `development`。
2. 所有日常业务代码、样式、测试和功能变更默认直接在 `development` 完成；纯文档维护适用第 2.0 节例外。
3. 小步提交，不覆盖或重置他人已提交的工作。
4. 发现暂时无法解决的问题，标记为「未完成」，记录现象、原因（未知则写原因待查）、影响、下一步和是否阻塞；不影响其他独立工作时继续推进。

Windows PowerShell 示例：

```powershell
cd C:\Users\shiniouyou\Documents\GitHub\daily_weekly_planner
git switch development
git pull origin development
git status
```

### 阶段 B：变更审查与风险评估

1. 检查实际 Diff、调用关系、页面入口、权限边界、数据影响和相关配置。
2. 按 `REVIEW.md` 将变更划分为 L1–L4 风险等级。
3. 优先采用最小必要修改；低风险变更不要求完整回归。
4. 功能代码与测试代码同步交付：新增功能同步补充适用测试；Bug 修复优先增加可复现问题的回归测试；修改既有行为时更新受影响测试。
5. 按风险选择单元/组件/API、集成或 Playwright E2E 测试；纯文档、纯样式或无行为变化的低风险修改可不新增应用测试，但需说明理由。
6. 不为追求测试数量重复编写低价值测试；不删除有效断言、不跳过失败测试来制造绿色结果。测试应可重复、隔离，不依赖生产数据或真实秘密。
4. 本地测试不是交付前置条件。用户设备无法运行测试时，不要求用户安装依赖、启动服务或执行命令。
5. 若某项验证必须依赖真实浏览器、手机、账号或本机专属环境，记录为未验证，并评估是否构成合并阻断。

### 阶段 C：GitHub Actions 自动化验证

1. 将 `development` 的变更提交并推送到 GitHub。
2. 优先使用 GitHub Actions 托管环境运行适用的静态检查、语法检查、单元测试、构建和 Playwright E2E。
   - development 上的常规提交也应触发适用的 CI；PR 检查继续作为合并前验证门槛。
   - CI 测试本次变更相关行为；Nightly E2E 负责整体回归与稳定性观察，不能替代针对性测试。
3. 对低风险、局部测试代码或文档变更，可依据 Diff 审查直接集成；不得为了形式要求重复执行耗时且无关的全量测试。
4. 对中高风险变更，尽可能在合并前运行相关 GitHub Actions；若工作流仅支持手动触发，应通过 GitHub Actions 页面或具备权限的自动化接口触发。
5. 对失败项先定位并修复；不得把失败、跳过或未执行描述为通过。
6. 记录 Actions run 链接和结果。若没有可用的 GitHub 托管测试，明确标记未验证并按风险决定是否阻断合并。

### 阶段 D：合并到 main

业务逻辑、代码、数据库、权限和部署变更合并到 `main` 前，必须先获得仓库所有者对本次集成的明确许可。纯文档维护不走本阶段，按第 2.0 节直接提交 `main` 并快进同步 `development`。获得业务集成许可后：

1. 再次确认 `development` 与 `main` 的差异、目标提交、冲突和验证结果。
2. 使用正常 PR 将 `development` 合并到 `main`；不强制推送、不重置公共分支、不绕过保护规则。
3. 检查 PR 的变更范围与自动化检查结果，确认合并目标为 `main`。
4. 合并后确认 `main` 已包含预期提交。

### 阶段 E：main 正式部署与验收

1. GitHub Pages 的正式发布来源固定为 `main`；**不得为了测试而把正式 Pages source 切换到 `development`**。
2. 合并后检查对应的 GitHub Pages build and deployment workflow。
3. 只有与目标 `main` 提交对应的 Pages 构建和部署均显示成功，才报告「已部署」。
4. 若工作流失败、仍在运行或无法确认对应提交，必须如实报告「未部署 / 部署中 / 状态待确认」。
5. 正式站地址： https://ouyangxinwei.github.io/daily_weekly_planner/
6. 用户端如仍显示旧页面，可先强制刷新（`Ctrl+F5`）；PWA 缓存也可能需要关闭后重新打开。

## 3. development 页面与正式站的边界

| 项目 | development 本地页面 | main 正式页面 |
|---|---|---|
| 访问方式 | `http://127.0.0.1:4173/` | GitHub Pages 正式网址 |
| 代码来源 | 本地 `development` 工作区 | GitHub `main` |
| 用途 | 开发过程页面、交互和联调验证 | 正式使用 |
| 自动发布 | 不自动覆盖正式站 | GitHub Actions 自动构建并部署 |
| 云端数据 | 当前可能连接正式 Supabase，写操作需谨慎 | 正式业务数据 |

GitHub Pages 当前只作为 `main` 的正式站点，不把 development 临时部署到同一网址。若将来需要远程 development 预览，应另行配置独立 staging hosting / URL，不能覆盖正式站。

## 4. Agent 分支例外

- `feat/agent-plan-steps` 是仓库所有者明确要求保留的 Agent 工作流实验分支。
- 该分支不属于日常功能开发分支，不应自动合并进 `development` 或 `main`。
- Agent 实验脚本按专项指南在该分支执行；任何将其成果纳入正式产品的操作，必须单独审查并取得所有者明确指示。
- 不得将其纳入普通临时分支清理。

## 5. 「未完成」事项记录规范

发现暂时无法解决的问题时，使用「未完成」状态或特殊标记，并记录：

- **现象：** 当前发生了什么，如何复现。
- **原因：** 已确认原因；尚未确认时写明「原因待查」，不得猜测。
- **影响：** 影响的功能、数据或用户流程。
- **下一步：** 后续检查/修复动作及必要依赖。
- **是否阻塞：** 若不影响其他独立工作，应继续推进并保留此记录。

未完成事项不能被写成已完成，也不能因暂时搁置而从文档中悄悄删除。

## 6. 每阶段交付检查清单

- [ ] 开发工作在最新的 `development` 分支进行。
- [ ] 代码、测试和相关文档已完成或明确标记未完成。
- [ ] 新增/修改/修复功能已同步评估并更新相关测试；不适用项已记录理由。
- [ ] 已完成 Diff、调用关系和风险等级审查。
- [ ] 已使用适用的 GitHub Actions 托管检查；未执行项及原因已如实记录。
- [ ] 需要真实设备/账号的项目已标记为未验证，并评估风险。
- [ ] 已获得所有者明确许可后才创建/合并到 `main` 的 PR。
- [ ] 合并后确认 Pages workflow 对应目标 main 提交并成功部署。
- [ ] Agent 保护分支未被修改或删除。

---

**固定原则：development 开发与风险审查 → 优先 GitHub Actions 托管验证（不要求用户本地测试）→ 经明确许可合并 main → 确认 GitHub Pages 正式部署成功。**
