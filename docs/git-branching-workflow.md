# Git 分支管理规范

> 本文定义项目统一的 Git 分支与 Pull Request（PR）工作流程。新功能开发默认遵循本规范；其他项目也可以复用这套轻量流程。

## 1. 分支结构

| 分支 | 类型 | 生命周期 | 用途 |
|---|---|---|---|
| `main` | 永久分支 | 长期保留 | 唯一稳定主分支，保存已确认并正式集成的项目代码 |
| `feat/<功能名称>` | 临时分支 | 单个功能周期 | 开发一个独立的新功能，完成后通过 PR 合并回 `main` |

### main 分支规则

- `main` 是唯一稳定主分支，永久保留。
- 所有正式功能、修复和文档变更最终都应集成到 `main`。
- 新功能原则上不得直接在 `main` 上开发或提交；先从最新的 `main` 创建独立工作分支。
- 不要为了某个短期功能长期保留额外的主开发分支。

### 功能分支命名

新功能使用以下格式：

```text
feat/<功能名称>
```

命名应简短、清晰，并能表达本次开发目标，例如：

```text
feat/customer-import
feat/project-dashboard
feat/task-reminders
```

每个独立功能使用自己的分支。不要把多个无关功能长期堆积在同一个分支中。

## 2. 标准开发流程

1. **同步主分支**：开始工作前，先获取远程最新状态，并以最新的 `main` 为基础。
2. **创建功能分支**：从 `main` 创建 `feat/<功能名称>`。
3. **独立开发**：在功能分支完成代码、必要的文档和最低限度的验证。
4. **创建 PR**：将功能分支提交到 `main`，在 PR 中说明变更内容、影响范围和验证结果。
5. **检查并合并**：确认变更适合合并、没有未解决的关键问题后，将 PR 合并到 `main`。
6. **清理远程分支**：确认 PR 已成功合并后，删除对应的远程功能分支。
7. **同步本地仓库**：切回 `main` 并拉取最新代码；删除已完成且不再需要的本地功能分支。

流程示意：

```text
main
  └── feat/<功能名称>
          ├── 开发与验证
          └── PR → main
                    └── 合并成功 → 删除远程 feat 分支
```

## 3. PR 与分支清理规则

- PR 的目标分支统一为 `main`。
- 只有确认 PR 已合并后，才删除对应的远程功能分支；PR 关闭但未合并时，不得当作已集成。
- 删除功能分支不会删除已经合并到 `main` 的提交和代码。
- 合并后应检查 `main` 中确实包含预期变更，再清理分支。
- 已合并的临时分支不应长期积累。分支清理是每次 PR 合并后的标准收尾步骤。
- `main` 永远不能作为清理对象。

## 4. 例外与安全边界

- 本规范中的 `feat/*` 用于新功能。确有必要时，纯修复或维护工作可以使用语义明确的临时分支前缀（例如 `fix/*`、`docs/*`）；它们同样应通过 PR 合并到 `main`，并在合并后清理。
- 历史遗留分支、尚未合并的工作分支或用户明确要求保留的分支，不应未经确认直接删除。
- **受保护分支（用户明确要求保留）：** `feat/agent-plan-steps` 是 Agent 工作流测试分支，保存 PLAN.md Step 1～5 的首次真实执行结果。即使已合并，也不属于"合并后清理"的对象；没有特殊需求不得删除本地或远程分支，删除前必须获得仓库所有者的明确确认。详见 [Agent 工作流实施指南](agent-workflow.md)。
- 不要通过强制推送或重置公共 `main` 来替代正常 PR 流程。
- 如果项目确实需要长期维护发布分支，应先在项目文档中说明原因、用途和维护责任；默认不创建长期分支。

## 5. 每次开发结束时的检查清单

- [ ] 本次工作在独立临时分支完成，而不是直接开发在 `main`。
- [ ] PR 的目标分支是 `main`。
- [ ] PR 已确认合并，且 `main` 包含预期变更。
- [ ] 已删除对应的远程临时分支。
- [ ] 本地已切回并同步最新 `main`。
- [ ] 没有误删 `main`、未合并分支或明确要求保留的历史分支。

---

**默认原则：一个功能一个临时分支；所有正式成果回到 `main`；PR 合并完成后及时清理临时分支。**


## 6. 默认自主执行与用户介入边界

除非用户对某项任务另有特别指示，AI 助手应按本工作流连续完成开发、必要验证、PR 检查、合并、部署确认和分支清理，不必在每个步骤等待单独批准。

- 常规代码实现、文档维护、必要版本记录、合理范围内的修复和常规 PR 合并，默认由 AI 助手直接完成。
- 合并前仍须检查 PR 目标分支、变更范围、冲突和关键验证结果；存在关键失败或明显风险时先处理，不得绕过。
- 合并后检查 `main` 是否包含预期提交，再确认对应部署流水线实际结果。只有部署成功才可报告线上可用。
- 合并后删除本次已合并且不再需要的临时远程分支；未合并、用户要求保留或仍承载其他工作的分支不得删除。
- 测试应与变更风险匹配，避免重复和低价值的全量测试。明确区分通过、失败、跳过和未执行。
- 用户明确禁用的工作流（例如 Nightly Playwright）不得擅自启用或运行。
- 浏览器/设备验收可提示用户稍后进行，不应自动假设用户已验收；若该验收不影响后续独立工作，可继续推进。

### 需要暂停商量的情形

只有在权限或外部授权不足、需要用户提供秘密信息、不可逆或高影响操作、重大需求歧义、重要架构取舍、安全风险或无法自行解决的冲突等情况下，才暂停并与用户商量。普通实现细节和常规交付步骤不需要逐项请示。

**默认协作原则：用户提出目标和重要方向，AI 助手负责连续执行可授权的工程工作；遇到真正的阻碍再沟通。**
