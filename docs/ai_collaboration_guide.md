# AI 协作开发指南

本文件记录计划网页的项目背景和迭代约定，供后续协作时作为产品资料。每次修改优先围绕一个目标，保持数据安全和已有功能。

## 1. 项目背景

这是一个原创的轻量个人计划网页，使用原生 HTML、CSS 和 JavaScript。主要文件为 `index.html`、`manifest.webmanifest`、`sw.js` 和 `icon.svg`。产品支持每日、每周、每月、每年计划，新增、编辑、删除、完成跟踪和浏览器本地存储，不含账号或后端。

## 2. 推荐需求格式

```text
目标：
当前表现或问题：
期望结果：
不可破坏的功能：
验收标准：
请说明修改文件、数据影响、验证方式，以及 Service Worker 缓存名是否需要升级。
```

## 3. 协作约定

- 尽量小范围修改，避免无关重写。
- 不要把用户输入作为 HTML 插入页面；应以文本方式显示。
- 修改本地数据结构时考虑已有用户数据的兼容迁移。
- 保持 JSON 备份导入校验与本地存储 schema 同步；任何格式错误不得覆盖当前数据。
- 备份导入采用整份替换；如新增合并模式，应明确展示冲突处理规则。
- 分类选项、旧数据默认类别和筛选／进度统计行为变化时，同步维护玩法说明、技术手册和 JSON 兼容逻辑。
- 修改星级优先级时保留 1–3 的数据边界、旧记录默认 1 星、SVG 图标显示和备份兼容行为。
- 临时计划仅在创建所在自然日／周／月内有效；调整周期标识或过期清理时同步检查备份恢复、完成记录清理及每周周一边界。
- “随机”视图是用户临时安排的独立清单，不代表系统随机抽取任务；保留与普通计划一致的编辑和追踪能力。
- 批量清理只能作用于当前选中周期；增加批量删除时须保留确认步骤，并清除关联完成记录。
- 修改页面功能后同步更新 `玩法与系统说明.md`、`技术手册.md` 和 `CHANGELOG.md`。
- 修改静态资源后更新 Service Worker 缓存名，避免线上客户端继续使用旧缓存。
- 说明功能是否需要 HTTPS、真实手机或浏览器手动确认。
- 不要声称已验证未实际检查的浏览器或设备行为。

- 修改提醒逻辑时保留本地时间语义、一次性通知、防重复标记和未完成计划过滤；明确页面关闭时不具备后台触发能力。

- 云端同步修改必须保留账号隔离和 RLS；浏览器中禁止放置 service_role。完整快照上传/下载是替换式操作，新增自动合并前应先设计删除墓碑、版本冲突与离线队列。

## V10.3 参考网站约定
新增计划字段时需兼容旧数据，并确认 JSON 导入导出与 Supabase JSONB 快照可保留该字段。参考网址只允许 HTTP/HTTPS，并通过安全的新标签页打开。



## V10.4 PDF 导出约定

- PDF 导出必须从当前已渲染的可见列表取数，遵循周期、搜索、分类筛选和排序，不自行重新查询全量数据。
- 每条计划在打印 CSS 中使用 `break-inside: avoid` 和 `page-break-inside: avoid`；备注和 URL 应可换行，中文需有字体回退。
- 浏览器打印转 PDF 为当前实现方案，不能声称为静默直接下载；用户需要在打印窗口选择“另存为 PDF”。
- 超过一页可打印高度的单条内容属于浏览器分页限制，必须在文档中如实说明；不引入未经授权的远程脚本或 PDF CDN。
- PDF 功能不改变数据 schema，不需要 Supabase SQL 迁移。


## 5. 默认自主开发与交付模式

### 固定分支规则

- `main` 是唯一日常开发分支；日常功能、修复、重构、文档和版本维护直接在 `main` 进行。
- `development` 暂停维护、暂时保留，不作为日常开发、测试、PR、合并或同步的前置条件。
- 日常开发不要求创建功能分支，也不要求 PR 合并流程。
- 除非用户明确要求或存在特殊技术需要，不主动恢复 development 的维护。
- GitHub Pages 仍从 `main` 正式发布；代码提交不等于部署成功。

### 默认由 AI 助手连续完成

1. 检查仓库、当前分支和工作区；日常修改在 `main` 进行。
2. 分析需求和影响范围，优先采用最小必要修改。
3. 优先使用真实页面验证关键功能；本地测试、自动化测试、构建和 Actions 按实际风险与需要选择，不作为每次开发前置条件。
4. 对能够自行判断和修复的问题直接处理；暂时无法解决且不影响其他独立工作的问题，标记「未完成」，记录现象、原因/待查、影响和下一步。
5. 按变更类型更新 README、产品规范、功能说明、技术手册、开发历史和当前交接文档；应用版本发布继续遵守 VERSION、三语 CHANGELOG、Release 和缓存版本规范。
6. 汇报修改文件、提交信息、实际验证结果、未完成事项和后续建议。
7. 需要发布时，检查 GitHub Pages 对应目标 main 提交的真实部署结果；只有确认部署成功后才能报告已部署。

### 必须暂停并与用户商量的情况

- 缺少必要的仓库、平台或外部服务权限，或遇到无法自行解决的技术阻碍。
- 需要用户提供密钥、账号授权、真实业务资料或只有用户本人才能完成的操作。
- 涉及不可逆的数据删除、真实资金交易、对外发送重要信息或其他高影响操作。
- 需求存在会实质改变产品方向、数据边界或架构选择的歧义。
- 出现重要代码冲突、安全风险或多个合理方案之间需要用户作出业务取舍。

### 测试与结果报告纪律

- 不把未执行的测试描述为通过；明确区分已通过、失败、跳过和未执行。
- 不为追求测试数量而反复运行耗时或重复测试；优先执行与本次变更风险直接相关的检查。
- GitHub Actions 不作为每次开发的前置条件；按风险、发布需要或用户要求运行。
- 用户明确禁用的 Nightly Playwright 等工作流不得擅自启用或运行。
- 代码提交到 `main` 不等于部署成功；必须核对正式部署结果。
- 需要真实浏览器、手机、用户账号或外部 API 密钥才能确认的画面行为，应标记为待用户验收。

### 用户与 AI 的分工

用户负责提出目标、确认重要产品方向、提供必要授权或资料，以及决定高影响操作。AI 助手负责获授权的代码开发、文档维护、必要验证、问题标注和交付报告。

## 6. Agent 工作流与多 Agent 协作

本仓库的 Agent 工作流实践和后续架构规划统一维护在 [Agent 工作流实施指南](agent-workflow.md)。

当前已设计并试运行的基础模式是：由本地 PowerShell 脚本读取 GitHub 上的 `PLAN.md`，选择一个待执行步骤，调用 Claude Code 完成限定范围内的修改，再由脚本检查差异并逐步 Commit / Push 到工作分支 `feat/agent-plan-steps`（不直接推送 `main`，不自动合并或部署；进入 `main` 需人工审阅 PR）。Claude Code 负责实现，脚本负责流程控制、范围校验和 Git 交付。

需要明确区分当前能力与目标架构：

- 当前基础模式是单个 Claude Code Worker 按步骤串行执行；循环处理多个步骤不等于已经实现多个独立 Agent。
- 目标架构是 Master Agent 拆分任务、Worker Agents 分别产出独立补丁、Master Agent 审查并控制集成。
- 多个 Worker 即使处理逻辑上互不依赖的任务，只要写入同一个文件，也不得并发修改同一工作区。应优先让 Worker 输出独立补丁，再由 Master Agent 串行应用和统一验收。
- Agent 的完成说明不能代替实际 Diff 检查；任务是否完成必须以代码差异和机器可验证的验收条件为准。
- 计划解析失败、文件范围越界、校验失败或 Git 状态不明确时应停止，不得自动跳过或强行标记完成。

详细执行步骤、PowerShell/Claude Code 分工、已遇到的问题、CheckOnly 检查方式、Master/Worker 职责和后续阶段见专项指南。
