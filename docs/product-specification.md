# 产品功能与业务规范

> 本文档定义「慢慢计划」当前产品要解决的问题、功能行为、业务对象、数据边界和验收原则。它刻意不绑定 JavaScript、数据库产品、框架或部署平台，作为未来使用其他开发语言重建产品时的共同依据。
>
> **当前参考实现：** 本仓库现有 JavaScript Web/PWA。  
> **规范状态：** 持续维护中；未明确的业务规则标记为「待确认」。  
> **状态说明：** 本文记录的是截至本次文档整理时从现有功能说明、专项设计及阶段记录中能够确认的状态，不代表未核实的线上部署状态。

## 1. 产品目标与范围

「慢慢计划」是个人使用的综合工作区，核心目标是帮助用户组织周期计划、工作事项、学习活动和个人资料，并逐步扩展到个人业务管理。

产品由多个具有明确职责和数据边界的工作区组成。未来实现可以更换编程语言、框架、数据库或部署方式，但应保持本文定义的用户可见行为、业务规则、数据语义和安全边界。

### 1.1 产品原则

1. 各工作区职责清晰，避免不同业务类型的数据混用。
2. 用户可以创建、查看、修改、完成、归档或删除自己管理的记录。
3. 重要数据操作应有明确反馈；导入、覆盖、删除等有风险的操作应先校验并在必要时要求确认。
4. 数据备份、恢复和同步必须明确作用范围，不应意外覆盖其他工作区。
5. 功能不可用、数据损坏、网络不可用和「尚未检查」应区分处理。
6. 安全、凭据和个人业务数据不得因诊断、日志或导出而泄露。
7. 功能状态必须如实记录；代码完成、自动测试通过、真实用户验证和线上部署成功是不同的事实。

## 3. 工作区与业务功能

### 3.1 计划工作区

**目的：** 管理具有时间周期、优先级和完成状态的个人计划。

核心行为：
- 支持每日、每周、每月、每年计划，以及每日、每周、每月随机临时计划视图。
- 允许新增、编辑、快速添加、完成/取消完成及删除计划。
- 计划可包含标题、备注、分类、优先级、日期/提醒和参考链接等信息。
- 支持搜索、分类筛选和多种排序；列表支持分页。
- 支持分类维护、归档、取消归档、回收站、恢复、永久删除及短时撤销。
- 周期计划在新周期开始时保留计划本身，完成状态按对应周期重新计算；随机临时计划仅在创建周期有效，过期后清理。
- 提醒依赖浏览器通知能力，页面关闭后不承诺后台触发。

**业务规则：**
- 优先级为 1–5 星。
- 每周周期以周一为起点。
- 搜索、筛选和排序影响列表展示；批量清理等危险操作应按明确的操作范围执行，而不是默默受当前筛选结果影响。
- 分类改名应保持关联记录一致；删除仍被使用的分类时，应先处理关联记录，不得造成悬空引用。
- 删除、恢复、归档、导入等操作失败时，不得显示虚假的成功结果或破坏原数据。

**状态：已实现。** 具体历史规则和版本变更见开发历史档案。

### 3.2 工作事项模块

**目的：** 管理独立于周期计划的工作事项。

核心行为：
- 工作事项有自己的记录、分类和工作状态。
- 支持新增、编辑、删除、搜索、筛选、归档、回收站、恢复和备份。
- 工作状态与计划完成状态是不同概念，不应强行共用同一套业务语义。
- 工作事项的数据范围与其他模块分开管理。

**状态：已实现。**

### 3.3 计划内外语任务

**目的：** 在计划工作区中管理与外语学习相关的待办任务。

此模块是计划任务的一种独立数据分区，不等同于独立外语学习工作区中的学习内容、练习和学习记录。

**状态：已实现。**

### 3.4 整理模块

**目的：** 管理需要分类保存和持续维护的个人资料条目。

核心行为：
- 资料类别包括书籍、电子产品、软件/APP、网站和其他等。
- 支持列表管理、分类、搜索、编辑、归档、回收站、恢复和 JSON 备份。
- 不使用每日/每周等计划周期。
- 资料数据独立于计划、工作和外语任务。

**状态：已实现。**

### 3.5 独立外语学习工作区

**目的：** 管理可持续学习的内容及其学习过程，而不只是把学习当作待办任务。

当前已记录的能力：
- 学习首页、学习内容、练习中心、错题管理、学习记录和数据管理。
- 学习内容可记录语言、类型、分类、单元、级别、提示、答案、选项、解析/笔记等信息。
- 学习状态包括未学习、学习中、已完成、需要复习、已掌握。
- 学习操作会形成学习记录并更新最近学习时间；编辑内容本身不应擅自改变学习状态。
- 练习中心优先处理需要复习的内容，并排除已掌握内容。
- 支持个人笔记、JSON 导入/导出和旧数据格式迁移。
- 删除学习内容时，既有学习记录和个人笔记的保留规则应遵循专项数据规范。

**数据边界：**
- 独立学习工作区与计划内外语任务是两套业务。
- 不参与计划工作区四模块整体备份和云端快照同步。
- 导入前校验并要求确认；失败时原数据保持不变。

**已知缺口：** 现有专项说明记录了词汇/语法专门学习、学习统计、学习时长、间隔重复、音频、云同步及完整三语界面等能力尚未实现。后续是否纳入产品范围需另行确认。

**状态：部分实现。** 具体字段、状态迁移、迁移兼容和导入限制以外语学习工作区专项文档为准。

**目的：** 分别组织个人成果记录和未来规划。

当前可确认的内容仅包括独立入口及其大致用途。具体实体、字段、状态、用户操作和验收标准尚未在现有当前功能说明中完整定义。

**状态：待确认。** 在补齐实际业务规则前，不应把它扩写成已完成的功能规格。

### 3.7 个人公司业务工作区

**目的：** 管理个人业务关系和业务推进过程。

#### 客户管理
- 支持客户列表、搜索、业务类型/状态筛选、分页。
- 支持新增、查看、编辑和删除客户。
- 客户管理基础 CRUD 已由用户真实浏览器验证。

**状态：已实现。**

#### 项目管理
- 项目可关联客户。
- 支持搜索、状态筛选、分页和 CRUD。
- 项目详情展示客户、状态、开始日期、预计完成日期、说明和进度。
- 项目进度支持手动设置或按任务完成比例自动计算，范围为 0–100 的整数百分比。
- 自动模式计算规则：已完成任务数 ÷ 项目任务总数 × 100%，四舍五入为整数；无任务时为 0%。
- 手动模式保留独立的手动进度值，任务新增、删除、状态变化或改派项目不得覆盖手动进度。
- 切换回手动模式时恢复最近一次手动进度；切换到自动模式时立即按当前任务重新计算。
- 自动进度由数据库事务触发器在任务创建、删除、状态变化、项目改派以及项目切换为自动模式时同步更新。
- 项目删除遇到下游引用时应受到关联保护，不得未经业务确认级联删除其他记录。

**状态：已实现。** 项目管理、详情、手动进度和 V10.45.0 的任务自动进度联动均已由用户真实浏览器验收通过。

#### 项目任务
- 一个项目可以关联多个独立任务；每个任务必须且只能归属一个项目。
- 任务支持新增、查看、编辑、删除、搜索、项目筛选、状态筛选和分页。
- 任务状态包括待处理、进行中、受阻和已完成。
- 任务可设置截止日期和说明；截止日期允许为空。
- 任务被项目引用时，项目不得直接删除；删除任务后不应影响项目和其他任务。

**状态：已实现。** V10.44.0 已合并、部署，并由用户确认真实浏览器验收通过。

#### 项目进度与任务联动
- 项目支持「手动设置」和「按任务自动计算」两种进度模式。
- 自动模式按已完成任务数占项目全部任务数的比例计算；所有任务等权，不按截止日期或工作量加权。
- 手动进度单独保存；自动模式不覆盖该值，切换回手动模式时恢复。
- 无任务的自动模式项目进度为 0%；增加、删除、完成/取消完成或改派任务后自动重新计算受影响的项目。
- 自动计算结果应在项目列表和项目详情保持一致，并在刷新后持久化。

**状态：已实现。** V10.45.0 已完成数据库迁移、company-api v5 部署、Pages 部署和用户真实浏览器验收。GitHub Actions Playwright 工作流曾停留在 Chromium 安装步骤，未取得 CI 测试通过结论；这与用户已完成的真实浏览器验收分别记录。

#### 业务跟进
- 跟进记录关联客户，并可选关联项目。
- 记录跟进方式、时间、结果、下次跟进日期、备注和处理状态。
- 跟进记录应能按客户/项目关系追溯。

**状态：部分实现。** 已有代码合并记录；线上部署和真实环境验收须单独确认。

#### 公司业务数据边界
- 客户、项目和跟进记录属于公司业务数据。
- 它们与计划、工作、外语任务、整理等个人计划数据分开存储和管理。
- 公司业务数据不应混入计划工作区的整体 JSON 备份或云端快照。
- 认证和 API 的具体契约见公司网站专项文档；凭据不得写入前端持久化存储或公开源码。

### 3.8 首页天气看板

**目的：** 提供固定地点的天气信息，辅助日常安排。

当前规则：
- 显示东京和横滨天气。
- 提供多日预报、当前天气摘要、缓存、手动刷新和离线缓存回退。
- 天气缓存独立于业务记录，不参与业务云同步。
- 当前天气服务和预报排序细节见天气看板专项文档。

**状态：已实现。**

### 3.9 系统级能力

- **界面语言：** 主应用支持简体中文、English、日本語。界面语言变化不应翻译用户输入的业务内容。
- **主题与响应式布局：** 支持深色/浅色主题和桌面、移动端布局。
- **PWA：** 支持可安装 Web 应用及静态资源缓存；线上可用状态以部署记录为准。
- **运行日志：** 诊断日志保存在当前设备，不上传业务云端；日志不可用不应阻断核心业务。
- **健康检查：** 对本地数据、日志存储、Service Worker、云端只读连接和部署信息等进行检查；「无法检查」与「检查失败」必须区分。
- **安全：** 不记录密码、Token、密钥、完整请求体或完整个人业务记录。

**状态：已实现。** 各工作区的语言覆盖和部署状态仍需按专项文档/实际环境判断。

## 4. 核心业务概念

以下是跨技术栈的概念模型，不规定具体表结构、字段命名、ORM 或序列化格式。

| 概念 | 业务含义 | 主要关系 / 约束 |
|---|---|---|
| 用户 | 使用个人工作区的人 | 访问需要经过产品定义的身份验证；不得在客户端明文保存密码 |
| 工作区 | 具有独立职责的数据和操作边界 | 一个产品可包含多个工作区；数据不能因共用界面而混用 |
| 计划 | 有周期、完成状态和优先级的安排 | 可关联分类；完成状态与周期标识相关 |
| 工作事项 | 需要推进的工作记录 | 拥有独立分类和工作状态 |
| 外语任务 | 计划工作区内的学习待办 | 与独立学习内容实体分离 |
| 整理资料 | 被分类管理的个人资料 | 不具有计划周期语义 |
| 学习内容 | 独立外语学习工作区中的学习单元 | 可关联学习记录和个人笔记 |
| 学习记录 | 某次对学习内容执行的学习操作 | 关联学习内容并保留操作时间和结果状态 |
| 学习笔记 | 用户对学习内容的个人补充 | 可关联学习内容；删除内容时的保留策略见专项规范 |
| 客户 | 公司业务中的客户主体 | 可关联多个项目和跟进记录 |
| 项目 | 围绕客户推进的业务事项 | 关联客户；被其他记录引用时需保护删除 |
| 项目任务 | 项目中可独立追踪的执行单元 | 必须关联一个项目；项目删除受任务引用保护 |
| 跟进记录 | 一次客户/项目沟通或业务推进记录 | 必须关联客户，可选关联项目 |
| 天气信息 | 外部天气服务返回的展示数据 | 属于外部信息缓存，不是用户业务记录 |
| 运行日志 | 当前设备上的诊断事件 | 不得承载完整业务数据或凭据，不参与业务同步 |

当前具体字段与数据类型以各工作区专项文档和现有实现为准；未来重建时应先确认业务语义，再决定技术字段映射。

## 5. 数据生命周期与隔离规则

### 5.1 数据分区

1. 计划、工作、计划内外语任务和整理资料分别管理。
2. 独立外语学习工作区单独管理。
3. 公司客户、项目、项目任务和跟进记录独立于个人计划数据。
4. 天气缓存与业务数据分离。
5. 运行日志与业务数据分离，且仅用于设备诊断。

### 5.2 备份与恢复

- 支持的业务模块应提供符合自身数据范围的 JSON 导出/导入能力。
- 导入前必须校验格式、版本/结构和必要字段，并向用户说明影响范围。
- 覆盖现有数据前应要求用户确认。
- 取消、校验失败或写入失败时，原数据必须保持可用，不得出现半写入状态。
- 单模块备份/恢复不得修改其他模块。
- 独立外语学习工作区和公司业务数据不属于计划工作区四模块整体备份范围。
- 具体导出范围和兼容规则应由每个工作区明确说明。

### 5.3 云端同步

- 当前计划工作区支持按模块分区的手动云端快照同步。
- 上传/下载是有明确覆盖语义的操作，不等同于实时双向合并。
- 单模块同步不得覆盖其他模块的云端分区。
- 独立外语学习工作区、天气缓存、运行日志和公司业务数据不应被错误纳入计划模块快照。
- 未来替换同步技术时，必须保持用户可见的覆盖范围、确认步骤、失败保护和数据隔离，除非另行批准改变业务行为。

## 6. 身份验证、权限与安全

- 用户身份验证必须由可信服务端或等效安全边界执行；纯客户端访问码不能被视为真实授权机制。
- 认证凭据不得写入源码、日志、URL、普通本地持久化或导出的业务文件。
- 访问公司业务 API 时，服务端必须验证请求身份和权限，不可仅信任前端传来的用户标识。
- 用户只能访问授权范围内的数据。
- 删除具有关联关系的数据时，应定义保护、解除关联或级联规则；不得默认级联删除。
- 诊断日志需脱敏并限制内容与保留范围。
- 所有外部 API 错误和网络不可用情况应有明确反馈，不应将未检查误报为成功或失败。

当前账号校验、RPC、Edge Function、数据库角色和权限配置均属于当前 JavaScript/Supabase 参考实现的技术细节，见技术手册及专项设计，不作为未来实现必须照搬的技术选型。

## 7. 外部服务与集成边界

| 集成 | 当前用途 | 产品层约束 |
|---|---|---|
| 云端数据服务 | 账号校验、计划模块快照同步、公司业务 API | 必须校验身份、隔离业务数据并保护凭据 |
| 天气服务 | 提供固定地点天气预报 | 外部数据失败时使用合理缓存/状态提示，不污染业务数据 |
| 静态托管与发布服务 | 发布 Web/PWA | 提交或构建成功不等于线上部署成功；需核对对应部署结果 |

具体供应商、端点、RPC 名称、请求头、数据库结构和部署流程放在技术手册及专项文档中。

## 8. 跨语言重建时必须保持的业务契约

未来使用其他开发语言重建时，应优先保持：

1. 工作区职责和数据隔离边界。
2. 每种记录的业务含义、状态和状态转换。
3. 计划周期规则、随机计划过期规则及优先级语义。
4. 客户、项目、项目任务、跟进之间的关联与删除保护规则。
5. 学习内容、学习记录、笔记之间的关系和保留规则。
6. JSON 导入/导出的业务范围、校验、确认、兼容和失败保护。
7. 云端同步的分区、覆盖语义和失败保护。
8. 身份验证、权限、凭据保护和日志脱敏原则。
9. 用户可见的操作反馈、异常状态和验收结果。

不要求保持：
- JavaScript 函数名、文件名或目录结构；
- 当前 LocalStorage key、IndexedDB 名称；
- 当前 Supabase 表、RPC、Edge Function 的内部实现（除非明确决定沿用数据/API 兼容契约）；
- 当前 CSS、DOM、组件或框架组织方式；
- 当前 GitHub Pages、Service Worker 的具体实现方式。

如需跨版本迁移已有用户数据，应单独定义旧数据读取、字段映射、校验、备份、迁移回滚和验收方案。

## 9. 通用验收原则

每个工作区的验收至少应覆盖：

- 核心新增、读取、编辑、删除和状态变化流程。
- 搜索、筛选、排序、分页等展示规则（适用时）。
- 关联记录的一致性和删除保护。
- 数据刷新/重新打开后的持久性。
- 导入、导出、备份和恢复范围。
- 取消、无效输入、网络失败、存储失败和部分失败路径。
- 权限边界、敏感信息保护和日志脱敏。
- 桌面、移动端和适用的界面语言。
- 代码测试、真实浏览器验收和线上部署状态分别记录。

具体测试数据、自动化命令和技术验证方式由当前实现或未来技术实现指南维护，不写死在本跨语言规范中。

## 11. 后续维护与多语言实现指南计划
