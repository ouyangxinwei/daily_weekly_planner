## 1. 目标与边界

在慢慢计划中逐步建立 AI 工作管理中心，管理 Agent、任务、调度、执行记录、报告、AI 服务商账号及预算。首个试点是跨仓库文档与实现一致性审查：

1. 从共同规范库读取当前有效规范。
2. 检查慢慢计划的文档、代码、页面、API、数据库迁移和部署证据。
3. 先用确定性程序和规则完成可自动化检查，不依赖付费 AI API。
4. 将结果生成 Markdown 报告，供用户次日阅读和人工决策。
5. 复杂语义判断以后作为可选 AI 步骤，不得成为日常任务运行的必要条件。

本系统是慢慢计划的管理/自动化能力，不是把现有开发 Agent 实验改名后直接当成生产调度器。当前只建立设计基线，不新增业务逻辑、数据库表、API、Edge Function、前端入口或部署服务。

### 2.3 前端和部署现状

- 主应用为原生 HTML/CSS/JavaScript，部署到 GitHub Pages；静态网页本身不能保证浏览器关闭后仍在每天 02:00 执行长任务。
- GitHub Actions 的自动测试/定时触发已按用户要求收缩；Pages 部署工作流按现有配置保留。日常 Agent 不以 GitHub Actions 为默认执行环境。
- 当前 Supabase 项目已有数据库和 Edge Functions，但尚未发现可承载长时间、可恢复跨批次任务的独立 Worker 服务。
- 用户的个人电脑通常关机，不应把“电脑每天凌晨保持开机”作为系统成立条件。
- 本项目不以当前是否拥有免费云平台、是否能绑定计费账户或是否有可用硬件作为设计前提。先完成平台无关的系统设计与可移植核心；实际部署时再按当时可用条件选择运行环境。
- 不承诺某个平台永久免费或永远可用。免费额度、注册验证、区域容量、资源回收、睡眠/暂停策略、网络和服务条款均属于部署时重新核实的事项。

## 3. 目标总体架构

```text
慢慢计划前端（GitHub Pages）
  └─ AI 工作管理中心：Agent / 任务 / 调度 / 报告 / 账号与预算
                 │ HTTPS API
                 ▼
独立 Agent 后端与调度器（常驻或受控唤醒）
  ├─ Scheduler：每天 02:00 JST 唤醒
  ├─ Task Orchestrator：任务队列、分块、断点和重试
  ├─ Rule Engine：无 AI 规则检查（第一阶段主执行路径）
  ├─ GitHub Reader：读取两个仓库及指定 Commit
  ├─ Report Builder：生成 Markdown 报告
  └─ Optional AI Adapter：需要时才调用外部模型
                 │
                 ├─ Supabase：任务状态、运行记录、预算和配置
                 ├─ GitHub API：读取规范库和目标项目
                 └─ 可选 AI Provider API：语义分析
```

职责边界：

- 前端负责展示、人工选择、审批和报告查看；不承担后台定时执行。
- Scheduler 负责准时启动任务；02:00 是启动时间，不代表任务必须在当晚完成。
- Worker 负责实际读取、检查、保存进度和生成报告；长任务允许跨日继续。
- Supabase 可作为管理数据与运行状态存储，但不能仅凭已有 Supabase 项目就认为长任务执行环境已具备。
- GitHub Actions 不作为日常 Agent 调度或执行环境；仅保留确有需要的仓库自动化和 Pages 发布。

### 3.1 可替换的软硬件执行平台清单

平台清单是候选池，不是当前采购/注册/部署决定。系统核心必须与运行平台解耦，平台可在实施后期按真实条件替换。

#### 硬件与托管形态

| 平台形态 | 可能选项 | 适用性 | 主要前提与风险 | 当前定位 |
|---|---|---|---|---|
| 个人 Windows / macOS / Linux 电脑 | Task Scheduler、cron、launchd | 适合本地开发、手动运行、故障排查和短期验证 | 电脑必须开机、联网且不能睡眠；用户电脑通常关机，因此不适合作为正式每日执行器 | 开发/备用 |
| 家用 NAS | Synology、QNAP 等支持 Docker/Container Station 的设备 | 可长期运行容器和定时任务，适合已有常开 NAS 的情况 | 设备需常开、网络稳定、CPU/内存/架构兼容；需要更新、备份和安全维护；新购硬件并非零成本 | 有现成设备时评估 |
| 低功耗迷你主机 / 单板机 | Intel NUC 类 Mini PC、x86 小主机、Raspberry Pi 等 | 可运行 Docker、Python Worker、系统 Cron，适合自主控制 | 需要购买硬件、供电、网络和维护；存储卡/磁盘可靠性需考虑 | 自建备选 |
| 云端虚拟机 | Oracle Cloud、其他云 VM、VPS | 可运行完整 Python/Docker Worker，支持长任务和系统级调度 | 免费资格、资源容量、信用卡验证、资源回收、区域可用性和计费条件各异；付费 VPS 需要预算 | 云端候选 |
| 托管容器/批处理 | Google Cloud Run Jobs、AWS ECS/Fargate 或 Batch、Azure Container Apps Jobs、Render Cron 等 | 不需要维护常驻主机，适合按需运行批次 | 通常需要云计费账户；免费额度与价格变化，超额可能收费；必须配置预算和停止策略 | 条件满足时评估 |

#### Worker 软件与调度软件

| 软件层 | 候选技术 | 建议职责 |
|---|---|---|
| 核心 Worker | Python CLI / Python package，优先提供 Docker 镜像 | GitHub 仓库读取、文件解析、规则检查、批次处理、报告生成 |
| 可移植容器 | Docker / OCI image | 保证本地、NAS、VM、托管容器之间运行环境一致 |
| 轻量函数运行时 | Supabase Edge Functions / Deno | Webhook、任务领取、轻量协调、状态回写；不预设其适合重型扫描 |
| 数据与检查点 | 现有 Supabase PostgreSQL；必要时本地 SQLite 作为开发/离线模式 | 任务状态、运行记录、检查点、锁、用量、报告元数据 |
| 调度器 | Linux cron / systemd timer、Windows Task Scheduler、NAS Scheduler、云端 Scheduler、Supabase Cron | 定时唤醒或触发 Worker；调度器不承载核心扫描逻辑 |
| 任务队列 | PostgreSQL 持久化队列 / 数据库任务表；必要时 Redis 或托管队列 | 任务分块、租约、重试、并发控制；先避免引入额外基础设施 |
| 仓库访问 | GitHub REST API / Git 数据读取 | 只读访问规范库和目标仓库，固定 Commit SHA |
| 报告存储 | Markdown 文件、Supabase Storage、受控 Git 分支 | 保留历史报告和证据，不自动修改业务代码或规范正文 |
| 可选 AI | Provider Adapter + 多账号/模型路由 | 只处理规则引擎无法可靠判断的语义问题；AI 不可用时核心流程仍可完成 |

Supabase 当前官方文档显示，托管 Edge Functions 有独立的运行时间、CPU 和内存限制；Supabase Cron 文档也建议单个 Job 不超过 10 分钟。因此它可以承担轻量调度/协调，但是否适合 Worker 本体必须通过小批次验证，不能直接假设它能运行大型仓库扫描：
- [Edge Functions Limits](https://supabase.com/docs/guides/functions/limits)
- [Supabase Cron](https://supabase.com/docs/guides/cron)
- [Scheduling Edge Functions](https://supabase.com/docs/guides/functions/schedule-functions)

所有平台在真正部署前都必须重新核实：免费层条件、是否要求计费账户/支付验证、超额计费行为、资源休眠/回收、最长执行时间、内存/CPU、持久磁盘、调度时区、密钥管理、出站网络、日志保留和数据区域。

#### 平台选择原则

1. 先开发平台无关的 Worker 核心，不因当前免费平台限制而改变业务逻辑。
2. 默认采用 Python + Docker 的可移植方案；如果后续证明纯 Deno/Edge Functions 更合适，可以替换执行适配器，但任务契约和检查结果格式保持一致。
3. Supabase 是优先复用的数据与状态存储，不等于必须由 Supabase 承担所有计算。
4. 电脑关机时，依赖个人电脑的定时方案自动失效；只有 NAS、常开小主机或云端执行环境能满足无人值守运行。
5. 如果所有候选平台在某个阶段都不满足条件，就暂停实际定时部署，保留手动运行/模拟运行能力，继续完成其他不依赖该平台的工作。
6. 任何免费层都不视为永久承诺；未经用户确认，不创建可能产生费用的资源、不启用付费升级、不绑定新的计费账户。


## 4. 第一阶段：AI-free 文档预审查

第一阶段默认不调用 AI API。用普通程序、GitHub API 和规则引擎完成确定性检查：

- 读取规范库目录结构、文件清单、规范编号、索引和相关内容。
- 读取目标仓库的目录、文档、代码、页面入口、API 路由、数据库 Migration、配置和部署说明。
- 检查规范条目是否有对应实现证据、文档是否缺失、链接是否失效、版本/命名是否冲突。
- 检查变更文件及其关联文档，标记新增、修改、删除。
- 保存检查证据：仓库、路径、Commit SHA、匹配位置/符号、检查规则和检查时间。
- 生成 Markdown 报告和待人工处理清单。

规则引擎不能仅凭 README 提到某功能或全文搜索到某个词，就判定功能已实现。应优先核对代码入口、调用关系、数据库定义、迁移状态和可验证部署证据。无法建立可靠证据链时标记「待验证」，不能猜测。

### 4.1 报告状态

| 状态 | 含义 |
|---|---|
| 已实现 / 已找到 | 找到足够的代码、页面、API、数据库或运行证据 |
| 部分实现 | 只覆盖规范的一部分 |
| 未实现 | 检查范围完整且证据足够，确认不存在对应实现 |
| 文档缺失 | 实际功能有证据，但缺少或缺少必要说明 |
| 不一致 | 规范、文档与实现之间存在冲突 |
| 待验证 | 有线索，但当前证据不足以判断 |
| 未检查 / 等待继续 | 尚未覆盖，不得视为未实现 |
| 检查失败 | API、权限、解析或工具错误导致无法完成检查 |

每份报告必须区分覆盖率、已检查、未检查、失败和待验证数量。不得把未检查项目统计为未实现。

### 4.2 报告存放

目标报告归档位置建议：

```text
docs/
  agent-reports/
    document-audit/
      README.md
      latest-report.md
      current-progress.md
      history/
        YYYY-MM-DD.md
```

- `latest-report.md`：最近一次完成或更新的审查报告。
- `current-progress.md`：全量扫描/增量扫描的断点和覆盖情况。
- `history/`：历史报告快照。
- `README.md`：报告结构、状态和证据定义。

报告生成后的 Git 提交/分支策略尚待实施阶段确认。无论采用报告分支、受限机器人提交或先保存到管理后台，都不得让审查 Agent 自动修改业务代码、规范正文或自动合并 `main`。

## 5. 大仓库扫描、分块与断点续查

不承诺两个仓库能在单次运行中扫描完毕。先测量，再配置批次。

### 5.1 首次全量扫描

1. 分别读取规范库和目标仓库的 Commit SHA，记录扫描基线。
2. 统计目录数、文件数、文件类型和可审查文件量。
3. 按规范目录/检查任务划分批次；文件量较大时再按文件数量和预计耗时细分。
4. 每批保存开始时间、完成时间、文件数、请求数、发现数、错误和结果引用。
5. 达到单次安全运行时限时，保存检查点并正常退出；下一次从未完成批次继续。
6. 所有批次完成后生成全量覆盖报告。

### 5.2 增量扫描

- 记录上次成功扫描的两个 Commit SHA。
- 根据 Git diff 识别新增、修改、删除文件。
- 重新检查变化文件及受影响的关联规范/代码；未变化且规则版本未变的结果可复用。
- 规则版本变化、扫描基线缺失或结果失效时，扩大重检范围。
- 定期安排全量复核，避免长期增量扫描遗漏关系变化。

### 5.3 限流、失败和一致性

- GitHub API 返回限流时，读取响应的恢复时间并暂停，不做无间隔重试。
- 运行失败时保留已完成批次、错误原因和恢复位置。
- 每次运行记录规范库与目标项目的 Commit SHA；若运行期间源仓库 HEAD 改变，本轮仍以记录的固定 SHA 读取，不能混用多个版本。
- 报告明确注明扫描基线；需要追最新规范时启动新一轮或后续增量扫描。
- 首次容量测试记录总文件数、请求数、耗时、单批处理量、限流情况和失败恢复情况，再确定批次大小与单次运行上限。
- 02:00 JST 触发的是调度器启动；扫描可以跨夜继续，直到完成或达到安全退出条件。

## 6. AI Provider、账号和预算

AI 是可选插件，不是 Agent 系统运行的前提。

- 一个 AI Provider 可配置多个账号。
- 同一 Provider 可配置多个模型及其能力/成本信息。
- 系统根据任务类型、账号状态、限流和预算推荐模型/账号；用户手动选择。
- 用户手动填写限流恢复时间；恢复时间之前不向该账号派发新调用。
- 密钥只保存在后端安全密钥存储/加密配置中；前端仅显示脱敏标识，不返回完整密钥。
- 每个任务限制执行时长、最大调用次数、重试次数和 AI 费用；系统另有月度总预算，并可按 Agent/账号设置子预算。
- 预算接近阈值时提醒；达到上限后暂停新的 AI 调用。AI 余额不足不应阻断无 AI 规则检查、调度、断点保存和报告生成。
- 用量/费用以 Provider 可核实的 usage/pricing 为准；无法确认的费用标记为估算，不伪装成实际账单。

具体 Provider、模型、预算金额、预警百分比和安全上限尚未确定，不在本设计中填入假定数值。

## 7. 权限与安全边界

| 操作 | 默认策略 |
|---|---|
| 读取两个指定仓库 | 允许；使用最小只读 GitHub 权限 |
| 执行规则检查、生成报告 | 允许 |
| 创建审查待办 | 允许，须使用独立 Agent 数据域 |
| 修改审查规则或共同规范正文 | 必须人工批准 |
| 修改应用代码、数据库结构或生产数据 | 必须人工批准 |
| 创建 PR / 推送业务代码 | 不属于第一阶段自动权限；未来另行审批 |
| 自动合并 `main`、自动部署 | 禁止 |

管理员入口当前只是只读观察视图，不是授权系统。未来 Agent 管理 API 必须有真正的服务端身份验证、角色/权限检查、审计记录和密钥隔离，不能把隐藏按钮当成安全控制。

## 8. 数据实体规划（仅概念，不是当前数据库）

实施前先对照当时的真实 schema，避免重复或过度拆表。可能需要的独立实体：

- Provider / Account / Model：供应商、账号和模型配置。
- Agent：Agent 类型、能力、权限和启用状态。
- Schedule：周期、时区、下次执行时间和启停状态。
- Task / Run / Run Step：任务定义、每次运行和分步结果。
- Budget / Usage Record：单次/月度预算、账号用量与成本。
- Report：报告元数据、文件位置、基线 SHA 和状态。
- Permission / Approval：可执行动作范围与人工批准记录。

这些名称只是概念清单，不代表必须一张概念对应一张表。应先设计数据所有权、生命周期、索引、RLS、保留期限和 API 契约，再决定表结构。不得复用计划快照或公司业务表来省事。

## 10. 分支与文档维护约定

本文件及 Agent 系统设计文档属于架构/维护文档，不属于业务逻辑变更：

- 此类纯文档更新可直接提交到 `main`，不需要为每次文档维护创建功能分支或 PR。
- 本次文档提交完成后，将 `development` 快进同步到同一 `main` 提交，使两个长期分支内容一致。
- 以后夜间 Agent 运行完成后，若它只生成审查报告/进度文档且不改业务逻辑，可按同一文档维护规则更新 `main`，再把 `development` 快进同步到相同提交。
- 若 `development` 已有独立提交或与 `main` 分叉，先检查并保留双方提交；不得强制推送或重置分支来制造一致。
- 业务逻辑、数据库、权限、部署配置和前端功能变更继续遵守 [Git 分支工作流](git-branching-workflow.md) 的正常审查与授权规则。
- 纯 Markdown 维护不修改应用 `VERSION`、`package.json` 版本、三语 CHANGELOG 或 Service Worker cache name；除非同一变更确实包含应用版本发布。
